# ReboHrome implementation and verification register

This register distinguishes implemented safeguards from remaining acceptance work. It does not claim that every possible defect has been found or that the full original audit plan is complete.

## Implemented

| Priority | Finding / trigger | Change / verification |
|---|---|---|
| P0 | Telegram payload could reach payment completion before authorization | Payment bridge removed; Telegram secret header is mandatory. |
| P0 | Manual card endpoints could complete a pending deposit without a provider confirmation | Endpoints return 410; repository completion stubs reject calls. |
| P0 | Duplicate or concurrent settlement could credit a deposit twice | Transactional ledger + balance + records; repeated settlement and failed-after-paid tests. |
| P0 | Vulnerable Next.js and compatible transitive packages | Next/eslint-config-next 15.5.25; updated compatible dependencies, PostCSS 8.5.28 override. No critical advisories in the last audit. |
| P1 | Missing Coinflow secret/amount could be accepted | Missing configuration, amount and non-USD currency fail closed. Existing production secret configuration still requires operational verification. |
| P1 | Cron authorization accepted spoofed headers | Exact mandatory bearer secret; unsigned requests reject. |
| P1 | Final provider status could hide a fulfillment failure | Finalization follows the committed financial result. MerchantPayd has `paid_unfulfilled`, jobs and an admin review page. |
| P1 | A lost webhook or late settlement could be ignored | Durable inbox, status reconciliation, leases and continued old-link checks. Unit tests cover late completion and unmatched early events. |
| P1 | External create reused sessions before account checks | MerchantPayd checks account, documents, KYC, maintenance and provider access before creation/reuse. |
| P1 | Weak login protection, password-reset flag and redirect handling | Database attempt limits, forced change-password route, session revocation, safe local redirect validation. |
| P1 | EUR amounts were treated as USD | New checkout accepts explicitly priced USD products; administrative balance adjustment requires USD. Other administrative financial editing paths remain in the review list below. |
| P2 | Stale client balances or receipt revisits caused local financial changes | Server account snapshots replace cached values; receipt/balance purchase no longer reapplies client deltas. |
| P2 | Cart persistence mixed users or concurrent saves | User-scoped local storage, atomic rows + version, stale-write conflicts; dedicated persistence test. |
| P2 | Optional Telegram prevented registration | Nullable handle and atomic user/profile/balance creation; full-schema local registration verified. |
| P2 | Database readiness was reported as healthy after errors | `/api/ready` and `/api/health` return 503 on DB/schema failure. |
| P2 | Runtime schema/registry changes and tracked local database | Explicit schema migration; runtime DDL disabled outside opted-in local setup; SQLite removed from Git tracking while preserving the local file. |

## MerchantPayd verification completed before deployment

- Unit tests: HMAC raw bytes, both authentication headers, fixed USD request, amount/currency/transaction checks, repeated settlement, failed-after-paid, idempotency conflicts, uncertain creation, rollback/retry of fulfillment, missing/early webhooks and second successful transaction review.
- Cart version and account isolation tests; redirect, cron and exact-money tests.
- Existing randomized-pack and Coinflow-country tests.
- Full-schema local repository integration: registration without Telegram, confirmed deposit credit and paid purchase fulfillment.
- TypeScript and complete production build; browser smoke checks are recorded separately during release verification.
- Authenticated MerchantPayd status probe succeeded with expected 404; no live payment was created.
- Production schema migration was rehearsed and applied with unchanged profile count and financial aggregates.

## Still required before enabling payments / declaring the full plan complete

1. Complete business acceptance for ordinary/blocked/reset-required accounts, KYC/document combinations, two browsers, changed cart, mobile checkout, stock exhaustion and crash recovery against the actual adapters. Unit fixtures do not substitute for all these scenarios.
2. Verify the merchant project's Cash App 4 availability and a controlled end-to-end payment. Confirm production legacy webhook secrets and provider-specific amount/ownership verification for every still-open payment.
3. Finish the review of administrative grants/account-data edits, atomic receipt saving and broadcast concurrency. They are not covered by the new payment-intent ledger.
4. Complete per-provider recovery acceptance for historical failed/expired/partially fulfilled payments. Do not repair financial history by automatically replaying credits.
5. Review remaining dependency advisories in legacy Solana/Wert SDK chains and remove unused checkout client integrations after historical support requirements are resolved.
6. Verify durable post-commit notifications and randomized probability refresh recovery across all legacy and Internal Wallet paths; MerchantPayd has a persisted job, some legacy refresh paths currently log a post-commit failure.

Smart-contract changes, deployment and transactions remain explicitly outside scope.

## 2026-09-15 release verification

RebohromePayment now offers Cash App and Bank Transfer in the payment-method selector. Credit Card, Apple Pay and Google Pay are visible and disabled. Tests verify `banking` requests, nullable classic-payment fields, method-specific idempotency and settlement checks. The full repository adapter also passed a Bank Transfer deposit and purchase simulation on the isolated database.

The latest run passed 16 payment/security/cart tests, TypeScript and the complete production build. Browser checks at desktop and mobile sizes passed with no JavaScript errors; both new methods could be selected, while all three paused methods were disabled. Authentication/KYC/document gates were exercised with local fixture accounts. Staged code and client artifacts contained none of the configured secrets. The final production dependency audit reported 0 critical, 0 high, 4 moderate and 2 low advisories.

This remains a deployment with new external payment creation disabled; the outstanding acceptance items above have not been declared complete.
